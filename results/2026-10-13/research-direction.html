ISAForge: optimize the cost of finding good instructions

The strongest research question is whether a learned, uncertainty-aware policy can find a useful custom instruction under a hardware budget with fewer expensive evaluations.

Recommended focus: one fixed processor and FPGA configuration, measured circuit costs, explicit instruction semantics, held-out workloads, and selection quality versus evaluation budget. Treat the LLM as a later experimental policy, compared against the same non-LLM tools.

Correct the assumptions before claiming speedup

A custom instruction does not necessarily slow the whole CPU clock. Its effect depends on whether it is combinational, pipelined, or multi-cycle and on the core interface. The CFU Playground interface explicitly supports multiple latency and handshake patterns. Choose one implementation contract before turning candidate delay into a runtime estimate.

Spike provides ISA execution and retired-instruction traces, not microarchitecture cycle timing. An isolated Yosys LUT count is a synthesis resource label, not physical area, routed timing, or whole-processor performance. Instruction reduction, hardware cost, and runtime speedup must remain separate measured or estimated quantities.

The experiment that would support a useful contribution

  1. Establish a reliable finite candidate pool. Use actual benchmark traces, legal I/O and live-out constraints, non-overlapping replacements, and exact RV32 semantics. Record workload and tool versions.
  2. Learn target-specific costs. Begin with actual synthesized LUT resources. Compare simple baselines, tree ensembles, and XGBoost. Select the model using only inner training folds; hold out programs and identical formulas from the outer test.
  3. Evaluate the decision, not only regression error. Under equal synthesis budgets, compare random, frequency, merit, predicted cost-aware ranking, and active learning. Report area violations, regret to an exhaustively measured pool oracle, evaluations, and wall time. Use a no-extension baseline.
  4. Add architectural evidence. Integrate one or two candidates into one chosen core. Measure correct execution, cycles, and the implemented clock constraint. Only then report runtime speedup and assess whether isolated-circuit estimates transfer.
  5. Test the agent's incremental value. Give an LLM the same observations, tools, and budget as active learning. Compare repeated seeds and include orchestration cost. A null result is useful.
