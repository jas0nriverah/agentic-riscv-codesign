# Ascon selector controller v2: stopped before candidate evaluation

This is a preserved controller failure, not a candidate result. The active Codex-chat selector reserved one of its three queries for `C01`, `and(xori(in0,-1),in1)`, then stopped with an unknown `ValueError`. It produced **zero candidate ledgers, zero candidate measurement directories, zero candidate evaluations, and zero target outcome rows**. It did not retry the charged reservation or inspect any target labels.

The root cause was in the wrapper path. `OneAttemptMixin.measure(candidate)` first asks the evaluator for its cached baseline. `_CandidateCapableEvaluator.measure` checked every requested name against the candidate pool and rejected `"baseline"` before delegating to the guarded evaluator. That exception occurred before any candidate compiler, simulator, synthesis, or route job.

The wrapper bug is fixed in the working tree: the baseline cache path now passes through, while candidate names still resolve against the frozen pool and both results still pass the Ascon KAT check. Additional checks bind ordered observations to durable terminal slots and key the adaptive GP cache by complete measured rows. Reviewing the raw event journal also found that the successful read-only `list_candidates` action was left marked `started` even though its public result was durably recorded: `setdefault` did not replace the existing status. The controller now closes successful read-only events as `complete`, requires terminal event records before continuing, and recovers an interrupted read-only call only when its result is already durable; otherwise it stops without retry. The archived event remains unchanged. These fake-only checks do not turn v2 into a valid experiment or demonstrate a real paid update. A new source-bound pushed release and a fresh, fully controlled campaign remain necessary.

The sealed v2 files and diagnosis are in [`controller-evidence/`](controller-evidence/), with machine-readable accounting in [`diagnosis.json`](diagnosis.json). Its update-policy distinction is documented in [paid-update semantics](../../docs/paid-update-semantics.md).
