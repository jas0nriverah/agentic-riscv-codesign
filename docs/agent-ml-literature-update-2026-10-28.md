# Agent, memory, transfer, and evaluation research update

**Purpose:** ground the current ISAForge agent/memory work in published methods and identify a defensible next ML experiment. This review supplements [the ISA/custom-instruction foundations](research-foundation.md). Literature establishes methods to adapt; it does not establish that ISAForge's graph, retrieval, XGBoost, or LLM agent improves processor performance.

## What established work contributes

| Li et al., “Efficient Design Space Exploration by Knowledge Transfer,” CODES+ISSS 2016, DOI [10.1145/2968456.2968457](https://doi.org/10.1145/2968456.2968457) | TrDSE groups applications using features from orthogonal-array samples and distribution statistics, then transfers models within related application clusters to reduce target-design queries. | A stronger transfer baseline than lexical similarity alone: test workload descriptors and source-target similarity with group-held-out evaluation. Its graph-encoded HLS pragma choices and workload setting differ substantially; ISAForge's pairwise XGBoost is a modest adaptation, not compareXplore. Use entire-workload/family splits and measure regret/feasible best-so-far. |

## Implications for memory and the knowledge graph

ISAForge has two distinct memories. **Episode memory** is the append-only host ledger of tool calls, charged attempts, failures, measured results, current incumbent, and finalization source. **Cross-workload evidence memory** is built only from host-approved historical training rows after workload and formula-family exclusions. The LLM receives a bounded, hash-linked subset; it does not get arbitrary repository access or unmeasured target labels. Historical outcome values may appear as prior evidence, but target outcomes enter only after the host authorizes and completes a measurement.

The current local graph is typed (`candidate`, `workload`, `expression_family`, `operator`, `measurement`), returns source-record hashes and evidence paths, and ranks by operator-set overlap. This mirrors the *provenance structure* idea in PROV-DM, but it is not a PROV-conformant implementation, graph database, graph neural network, performance model, or validated retrieval algorithm. Its operator-overlap score must never be described as predicted speedup. The graph should remain an ablation arm until it improves decisions on held-out workloads under identical context and measurement budgets.

Memory protections to keep:

- Freeze the full target roster and its workload/family scope at episode start; reject roster drift on every decision.
- Check target workload and every target family before indexing and again at retrieval; do not reduce this exclusion to only the candidates still unattempted.
- Keep historical labels traceable to immutable record hashes and model/data versions. Treat retrieved text as untrusted evidence, never as tool instructions.
- Separate scores for retrieval relevance, context size, tool reliability, and selected-design quality. A memory hit is not a prediction and a larger context is not automatically better.
- Use only memory modes with a declared retrieval contract. Current semantic retrieval is local TF-IDF plus truncated-SVD (LSA), not pretrained embeddings; there is no vector database, general-document RAG, chunker, or reranker in the selector.

## Evals and human review

Use a layered evaluation rather than an LLM judge for everything:

1. **Deterministic protocol evals:** schema, exact IDs, invalid/repeated actions, call/measurement charging, stale finalization, host fallback, target-label privacy, and exported provenance. The host is the judge.
2. **Repeated live-agent reliability:** on frozen target episodes, run repeated trials with fixed model/prompt/tool versions; report completion and valid-tool rates, pass$^k$, escalation/fallback rates, tokens, latency, and cost. The API key is currently unavailable, so this live evaluation is not run.
3. **Selection-quality evals:** keep whole workloads and operation families held out; reveal only permitted paid observations; compare same candidate pool, features, area/timing limits, and attempt/time budgets. The primary outcomes are best verified feasible whole-program speedup after each budget and regret to a complete measured-pool oracle. Report every failure and incomplete pool.
4. **Human-in-the-loop:** researchers review the frozen target/program, legality and family exclusions, preregistration, and authorization of expensive native measurement. Record decisions, reasons, elapsed review time, and any changes. The current gate is a protocol/release responsibility, not an interactive runtime approval feature. Human review must happen before hidden test labels are exposed.
5. **Optional explanation review:** a blinded human rubric is primary for explanation clarity and evidence citation. An LLM judge may be a secondary rubric scorer with human calibration. It must never judge candidate legality, correctness, feasibility, cycles, area, timing, or regret.

## Best next ML experiment and stopping rule

Current audited data contain 122 verified speedup labels across 14 workload groups; all measured whole-program cycle deltas agree with independently calibrated latency. The consumed-data screen shows pairwise XGBoost is only a budget-specific challenger: merit/latency remains stronger at three measurements. Therefore another speedup regressor or model-family sweep on the same labels is not justified.

The current pairwise XGBoost ranker uses 35 hand-built structural/profile features: candidate size, dynamic runs/places, instruction savings, tree depth, input/constant counts, and an operation histogram. It is an ordering model, not a calibrated speedup predictor. Its performance features omit operator order and immediate placement. The 122 candidate rows are nested within only 14 workload groups, and 12 groups have complete measured-pool oracles. Treat the workload group as the independent unit; seeds and candidates do not inflate sample size.

On the consumed grouped holdout, define regret advantage as `merit regret - pairwise XGBoost regret`; positive values favor XGBoost. The paired workload estimates are +0.290 percentage points at B1 (95% interval -0.065 to +0.849), +0.027 at B2 (-0.097 to +0.177), and -0.056 at B3 (-0.167 to +0.000). The first two intervals cross zero; at B3 merit wins. This makes pairwise XGBoost the predeclared challenger to test, not the selected winner. Timing is not yet a discriminating label: every successful measured design clears the 12 MHz floor by more than 20 MHz. Hardware feasibility remains mostly area-boundary selection.

The strongest next model question is whether the frozen pairwise XGBoost policy improves *prospective constrained selection* over merit and non-agent active learning on a source-family-disjoint, untouched eligible workload. Train only on historical whole-workload groups; keep the held-out candidate outcomes hidden except for charged queries. Compare frequency, merit/calibrated-latency, random, the existing uncertainty/cost-aware policy, pairwise XGBoost, and a measured oracle on the same pool. Evaluate B1/B2/B3 prefixes, feasible speedup and regret when oracle-complete, area/timing failures, actual per-candidate evaluation time, and model/refit overhead. If no fresh eligible independent target can clear existing workload/legal-candidate gates, stop ML tuning and report that blocker rather than relaxing the gates.

For a confirmatory campaign, freeze each full query order before the first target label; B1/B2/B3 are prefixes of that same order. Keep failures charged, unknown/censored outcomes unlabeled, and oracle regret unknown for incomplete pools. Predeclare one primary budget and compare paired workload-level differences with uncertainty intervals. Include pairwise ranker, merit (primary operational control), frequency, calibrated-latency/timing-aware heuristic, latency-cost heuristic, factorized-feasibility XGBoost, seeded random, and non-agent active learning. Separately account for model fit/inference, target evaluation count, actual native elapsed time, and human review time. Promote no policy unless it improves the preregistered measured feasible-performance endpoint; rank metrics and MAE alone are not sufficient.

For a future one-to-three-instruction result, enumerate compatible sets, enforce the common area/timing budget, and measure the modified program and integrated processor for each selected set. Never sum single-instruction speedups or LUT deltas as if they were independent. Keep a null or negative result if merit remains better.

## Workload-source search status

The expanded source census across Embench, BEEBS, TACLeBench, MiBench, CHStone and MachSuite found no further workload that can currently clear the unchanged source, oracle, license, memory, candidate-pool and opportunity gates. The closest MiBench lead, GSM 06.10, has a fixed 21,312-byte input, larger than the whole code/data partition; CHStone's small `mips` case is a bubble-sort program in a consumed family. A pinned MachSuite source review found that Viterbi does include a reference-path checker, but its standard double-precision tables and DP stack require at least 138,008 bytes (about 135 KiB) before code, far beyond the 8-KiB RAM contract. The closest untouched BEEBS source, Levenshtein, has already been tried twice: original target discovery failed during compilation, and a separate strlen-adapted context failed the frozen twelve-candidate gate. Preserve these source and target rejections; do not rerun or tune around them. Public sources become training data only after compatible ISAForge labels exist; published outcomes on different processors are not pooled as if they were PicoRV32 labels. See the [full source census](training-dataset-census-2026-10-28.md) for primary links and precise limits.
